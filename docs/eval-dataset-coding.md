# Coding Agent 评测集（v1）— 手动录入用

给 mini-coding-agent「评测」模块准备的一套 **coding 相关**测试用例，替代内置的
「示例评测集：基础问答」（那三条是 23×47、翻译、减法的通用问答，跟编码能力无关，
跑出来的分数写进简历会被问穿）。

本文档包含：5 条用例的完整内容（可直接复制进页面）、跑之前必须知道的两个坑、
两种对比打法、以及结果怎么解读。

---

## 一、这套用例测什么

5 条用例覆盖 coding agent 绑定的全部 5 个内置工具，难度递增：

| # | 用例 | 考察能力 | 用到的工具 | 是否改动工作区 |
| --- | --- | --- | --- | --- |
| 1 | 目录勘察 | 列目录 + 读文件 | list_dir | 否 |
| 2 | 写新文件并自测 | 写文件 + 执行 | file + shell | 是（eval-sandbox/） |
| 3 | Shell 计算与环境感知 | 执行命令、感知工作目录 | shell | 否 |
| 4 | 多文件创建 + 检索 | 写文件 + 搜索定位 | file + grep | 是（eval-sandbox/） |
| 5 | 改既有代码 + 回归自检 | 修改文件 + 自测 | file/edit_file + shell | 是（eval-sandbox/） |

所有写操作都限定在工作区的 `eval-sandbox/` 子目录下，跑完删掉这一个目录即可清理干净。

## 二、跑之前必读（两个坑）

### 坑 1：评测会真实写入 Agent 的工作区

`coding-agent` 的工作区是 `D:/zhuomian/test_workspace`。评测运行时 Agent 就在这个目录里干活，
**用例 2/4/5 创建的文件会真的落盘**到 `D:/zhuomian/test_workspace/eval-sandbox/`。

- 跑完清理：直接删掉 `D:/zhuomian/test_workspace/eval-sandbox/` 整个目录。
- 用例 1、3 只读，不产生任何文件。

### 坑 2：当前档位可能让用例「跑不完」（重要）

`coding-agent` 现在处于 **阶段确认** 档位（`autonomy_mode = stage_confirm`）。这个档位下 Runtime
会额外给模型两个工具：`submit_stage_plan`（制定阶段计划）和 `finish_stage`（阶段收尾）。

问题出在 `submit_stage_plan`：如果模型把某条用例当成「从 0 到 1 的新项目」，它会提交阶段计划
然后**直接结束这一轮**。而评测执行器只把「正常完成」和「阶段完成」当作成功，
`submit_stage_plan` 结束的运行会被判 **执行失败、不评分**。

**对策（二选一）：**

- **做法 A（推荐）**：跑评测前把档位临时改成「高度自主」，跑完改回。高度自主档位不提供这两个
  收尾工具，Agent 就是老老实实跑工具循环。改一行配置（见第四节命令），不用重启后端。
- **做法 B**：不改配置。下面 5 条用例的问题里我已经写了「直接动手，不需要制定阶段计划」的引导语，
  多数情况不会触发。跑完去任务详情里看一眼，哪条显示「执行失败」就重跑那一条。

## 三、用例内容（复制粘贴用）

> 每条用例对应页面「新增用例」弹窗里的三个输入框：**用户问题（必填）/ 期望答案 / 评分要求**，
> 一一对应下面的三段。只复制代码块里的文字，首尾的 ``` 围栏和【】小标题不要粘进去；
> 多行文本直接整段粘贴，换行会保留。

### 用例 1 — 目录勘察

**【用户问题】**

```
查看当前工作区的顶层结构，只依据实际查看结果回答，不要猜测：
1) 顶层有哪些子目录？
2) 顶层有哪些 .md 文件？
请说明你是用什么方式查看的。
```

**【期望答案】**

```
顶层子目录：backend、frontend、tests、scripts、data（若额外列出 .gitignore、.mini-agent、run.py 等隐藏项或文件，不扣分）。
顶层 .md 文件：README.md、handoff-阶段一.md、handoff-阶段二.md、handoff-阶段三.md、handoff-阶段四.md（共 5 个）。
```

**【评分要求】**

```
对照参考答案核对准确性：五个子目录（backend/frontend/tests/scripts/data）缺一个或错一个扣 10 分；五个 .md 文件缺一个或错一个扣 10 分。回答必须体现是通过列目录/读文件实际获得的，纯凭空罗列且与实际不符最高给 50 分。全部准确给 90-100 分。
```

### 用例 2 — 写新文件并自测

**【用户问题】**

```
直接动手完成，不需要制定阶段计划。
在当前工作区下新建 eval-sandbox 目录，并在其中创建 stats.py，实现函数 summarize(numbers)，返回一个字典，包含 count（元素个数）、sum（总和）、max（最大值）、min（最小值）四个键；当 numbers 为空列表时，四个值都返回 0。
写完后用 Shell 实际运行一次自测，分别打印 summarize([3, 1, 4, 1, 5]) 和 summarize([]) 的结果。
回答中必须贴出 stats.py 的完整代码，以及两次真实运行的输出。
```

**【期望答案】**

```
stats.py 实现 summarize(numbers)：对 [3, 1, 4, 1, 5] 返回 {"count": 5, "sum": 14, "max": 5, "min": 1}；对空列表返回 {"count": 0, "sum": 0, "max": 0, "min": 0}。
```

**【评分要求】**

```
① 回答包含 stats.py 的完整代码，缺失最高给 50 分；
② 包含两次真实运行的输出，只声称"已测试"但没有输出最高给 70 分；
③ [3,1,4,1,5] 的结果必须为 count=5、sum=14、max=5、min=1，每错一项扣 15 分；
④ 空列表必须返回四个 0 且不抛异常，抛异常或返回 None 扣 20 分。
```

### 用例 4 — 多文件创建 + 检索

**【用户问题】**

```
直接动手完成，不需要制定阶段计划。
在 eval-sandbox 目录下创建三个 Python 文件：a.py 定义函数 add(a, b) 返回两数之和；b.py 定义函数 sub(a, b) 返回两数之差；c.py 定义函数 mul(a, b) 返回两数之积。
然后在 eval-sandbox 目录范围内搜索函数定义，回答：add、sub、mul 三个函数分别位于哪个文件？除了它们，这个目录里还有没有其他函数定义？
把搜索命令和输出贴出来。
```

**【期望答案】**

```
add 在 a.py、sub 在 b.py、mul 在 c.py。
若此前已跑过用例 2（存在 stats.py），则目录内还有 summarize（在 stats.py）；否则没有其他函数定义。
```

**【评分要求】**

```
① 三个文件均被创建（过程或回答中可见写入动作）；
② 使用搜索/读取能力得出结论，而非凭空回答；
③ 三个函数的文件归属必须正确（add→a.py、sub→b.py、mul→c.py），每错一项扣 20 分；
④ 对"是否还有其他函数定义"的回答与目录实际情况一致即可，不强制。

### 用例 5 — 改既有代码 + 回归自检

**【用户问题】**

```
直接动手完成，不需要制定阶段计划。
在 eval-sandbox 目录下创建 wordcount.py，实现函数 count_words(text)：按空格切分，返回单词数量；空字符串返回 0。
然后修改这个文件，为函数增加一个参数 min_len（默认值 2）：长度小于 min_len 的单词不计入。
修改完成后用 Shell 实际运行三次并贴出输出：count_words("a bb ccc")、count_words("")、count_words("a bb ccc", min_len=1)。
回答中贴出最终的完整代码。
```

**【期望答案】**

```
count_words("a bb ccc") = 2（"a" 长度 1 被忽略，bb、ccc 保留）
count_words("") = 0
count_words("a bb ccc", min_len=1) = 3（三个词全部计入）
```

**【评分要求】**

```
① 最终代码含 min_len 参数且默认值为 2，缺失最高给 50 分；
② 三次输出分别为 2、0、3，每错一个扣 15 分；
③ 体现是在已有文件上修改（而非另建无关文件）；
④ 贴出的代码应可直接运行，明显语法错误扣 30 分。
```

## 四、怎么跑

### 方式一：一键录入（省事）

前置：后端已在 `127.0.0.1:8001` 运行。

```bash
cd backend
uv run python scripts/import_coding_eval_dataset.py
```

脚本会创建名为「Coding Agent 基础能力（v1）」的数据集并灌入 5 条用例；重复执行会提示已存在并跳过。
它做的事和你在页面上手填完全一样，只是免去 15 次复制粘贴。

### 方式二：手动录入（严格对照页面，逐步）

**第 1 步 · 新建数据集**

1. 打开「评测」页，确认顶部标签停在 **「数据集」**；
2. 点右上 **「新建数据集」**，弹窗里只有两个框：
   - 名称（必填）：`Coding Agent 基础能力（v1）`
   - 说明（可选）：可填「5 条编码任务用例，覆盖列目录、文件读写、Shell 执行与代码检索」，也可以不填
3. 点「保存」。左侧数据集列表会出现它，**单击选中**，右侧进入数据集详情（显示「0 条用例」）。

**第 2 步 · 逐条添加用例（重复 5 次）**

1. 在右侧数据集详情里点 **「新增用例」**，弹窗有三个框：**用户问题（必填）/ 期望答案 / 评分要求**；
2. 把第三节用例 1 的三段文字分别粘进三个框（只要代码块里的文字，不要 ``` 围栏和【】标题），点保存；
3. 回到列表能看到 1 行，继续点「新增用例」加第 2 条……直到 5 条加完。
   右侧表格显示「5 条用例」就对了。

> 提示：数据集弹窗里**填不了用例**——用例是选中数据集后在右侧「新增用例」里逐条加的，别在弹窗里找。

**第 3 步 · 建任务并启动**

1. 切到顶部 **「评测任务」** 标签 → 点 **「新建任务」**（弹窗标题是「新建评测任务」），弹窗里选：
   - **待评测 Agent**：coding-agent
   - **评测数据集**：Coding Agent 基础能力（v1）
   - **评分模型**：建议 `deepseek-v4-pro`（判分比 flash 稳，且不与被测模型同一个，避免自我偏好）
   - **通过分数（0–100）**：保持默认 60
   - **允许工具**：**勾上**（这套用例本来就是测工具能力的）
2. 点 **「保存并启动」** 立即开跑；也可以点「保存为待运行」，之后在这个任务的详情页点 **「启动评测」**。

**第 4 步 · 看结果**

5 条用例顺序跑（每条 = 一次完整 Agent 运行 + 一次评分），任务详情实时刷新：
状态徽章（待运行 / 执行中 / 已完成 / 已中断）+ 统计条（总用例、已完成、通过、未通过、
执行失败、评分失败、平均分、过程均分）。点开每条用例能看得分、评分理由、过程分与理由，
并可跳到对应的运行记录看 Agent 当时怎么跑的。页面刷新不影响执行；
**别中途重启后端**，否则任务会被标成「已中断」。

**第 5 步 · 回归对比**

- 前提：同一数据集的**两个任务都已跑完**；
- 在任一任务详情里展开 **「回归对比（V1 → V2）」** 折叠面板：左下拉选基准任务（V1）、
  右下拉选对比任务（V2），点「开始对比」；
- 注意：下拉里只会出现**同一数据集且已跑完**的任务，别的任务不出现是正常的；
- 结果包含：平均分 / 过程均分 / 通过数的 V1→V2 变化与差值，以及逐用例的分数对照（涨绿跌红）。

### （可选）跑之前改档位

如果担心第二·坑 2 说的「提交计划就结束」，跑评测前执行（在 `backend/` 目录）：

```bash
python -c "import sqlite3; c=sqlite3.connect('mini_agent.db'); c.execute(\"update agents set autonomy_mode='autonomous' where id=1\"); c.commit(); print('档位已改为高度自主')"
```

跑完恢复原状：

```bash
python -c "import sqlite3; c=sqlite3.connect('mini_agent.db'); c.execute(\"update agents set autonomy_mode='stage_confirm' where id=1\"); c.commit(); print('档位已恢复为阶段确认')"
```

改的是 agent 的默认档位，下次运行即刻生效，不用重启后端。

## 五、两种对比打法（回归对比要用同一数据集）

「回归对比」要求两个任务来自**同一个数据集**，所以同一套用例跑两遍才有对比数据。

### 打法 A：工具开 vs 工具关（零配置改动，推荐先跑这个）

操作：按第 3 步建**两个任务**，其余选项完全一样，只有「允许工具」一个勾选框不同——

- 任务 1：**勾上**（Agent 正常干活）
- 任务 2：**不勾**（Agent 拿不到任何工具定义，只能靠对话空答）

两个都跑完后，在任务详情的「回归对比（V1 → V2）」面板里选这两个任务开始对比。
预期结论很直白：关工具时用例 2/4/5 直接崩（写不了文件、跑不了命令），用例 1/3 也答不准。

结论会很直白：关工具时用例 2/4/5 直接崩（写不了文件、跑不了命令），用例 1/3 也答不准。
简历/面试的价值在于证明「这份能力来自 Runtime + 工具链，不是模型裸跑」。说辞示例：
「同一数据集下，关闭工具后通过率从 X% 掉到 Y%，说明 Agent 的实际产出能力主要由工具执行闭环支撑」。

### 打法 B：模型对比（更贴近真实迭代）

- 任务 1：被测 Agent = coding-agent（当前绑的是 deepseek-v4-flash）
- 任务 2：先到「Agent 管理」页**新建一个 Agent**，绑 `deepseek-v4-pro` 模型、
  勾上同样的 5 个工具（shell / file / edit_file / list_dir / grep），再用它跑同一数据集

预期 pro 的结果分和过程分更高（工具调用更克制、更少绕路）。这条能讲
「模型能力 + 提示词对 Agent 表现的量化影响」。

预期 pro 的结果分和过程分更高（工具调用更克制、更少绕路）。这条能讲「模型能力 + 提示词
对 Agent 表现的量化影响」。

> 提示：如果只是想知道「有没有数据」，打法 A 最省事，两次点击就够。

## 六、结果怎么看 / 能写进简历什么

任务详情里能拿到，页面统计区也会算出：

- **平均分（average_score）**：所有用例结果质量分的均值，单位 0-100。
- **平均过程分（average_process_score）**：工具使用合理性的均值——这是这套集子比通用问答有意义的地方，
  能讲「同一条任务，工具调用次数从 N 次降到 M 次」这类故事。
- **通过率**：结果分 ≥ 通过分（60）的用例占比。
- **回归对比**：两个任务的逐用例分数差、平均分差、通过率差。

**能写进简历的**（跑完才有真数字，替换 X/Y）：
- 「自建 5 条编码任务评测集，覆盖文件读写 / Shell 执行 / 代码检索；同一数据集做 A/B 回归对比，
  工具关闭时通过率由 X% 降至 Y%」
- 「引入 LLM Judge 双维度评分（结果质量 + 过程合理性），过程分从 X 提升到 Y，对应工具调用次数下降」

**不能写的**：任何没跑出来的数字。跑之前评测相关条目只写机制（「支持 LLM Judge 过程评分与回归对比」），
不写跑分。
