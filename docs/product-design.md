# mini-coding-agent 产品设计文档

> 定位速览：本地优先的 Web 全栈 Coding Agent 工作台。目标不是 Demo，而是一个有工程深度、能独立完成中小型 Web 全栈项目、且每一层都可被开发者吃透和讲清楚的 Agent 产品。

> 状态标记：✅ 已完成　🚧 部分完成/进行中　📋 已设计未实现

## 一、产品定位

- **服务对象**：开发者个人（先服务作者本人，用于真实开发提效与求职作品）。
- **产品形态**：网页工作台。用户创建 Agent、绑定模型/工具/工作区，聊天派活；Agent 在本机工作区里读写代码、执行命令、启动服务、跑测试，全程可观察、可干预、可回放。
- **目标场景**：中小型 Web 全栈项目——从前端、后端、联调到测试、启动、验收，由 Agent 分阶段独立完成，高风险操作经人工审批。
- **不做什么**：不做多租户 SaaS、不追求通用聊天助手、不做企业级平台（对应简历口径：个人开发提效 + Agent 工程化探索）。

## 二、核心设计理念

1. **轻量 Agent Core + 扩展丰富能力**（参考 Pi Agent 思想）：核心只保留执行循环、上下文管理、工具协议；缺能力不等于加专用工具，优先靠少量通用工具 + Skills/MCP 扩展。
2. **代码强制而非提示词服从**：可靠性靠执行层机制落实（工作区沙箱、命令黑名单、审批、超时与树杀），不指望模型听提示词就守规矩。
3. **本地优先**：数据与执行都在本机（SQLite + 本机工作区 + 本机命令），后端只监听 127.0.0.1。
4. **一切可观察、可回放**：一次消息对应一条 Run，工具调用、审批、压缩等事件全部落库，可事后回放。
5. **评测伴随开发**：每开发一项 Agent 能力，同步补验证与评测，用客观数据（测试通过率、工具调用/失败数、耗时、Token、审批数）说明能力变化，不只看总分。

## 三、整体架构

```
前端（Vue3 + TS + Vite + Pinia）
  └─ 相对路径 /api，Vite 代理到本机后端
后端（Python 3.12 + FastAPI + SQLAlchemy + Alembic + SQLite）
  ├─ API 路由层（聊天 / Agent / 模型 / 工具 / MCP / Skills / 运行记录 / 评测）
  ├─ AgentRuntime（唯一执行核心：模型循环、工具调度、上下文容量管理与自动压缩、审批挂钩）
  ├─ 工具层（统一执行入口 executor + 内置工具 + MCP + Skills）
  ├─ 治理层（工作区沙箱、命令黑名单、执行前人工审批、Shell 后台任务与整树击杀）
  └─ 记录层（run_recorder：Run / 安全事件 / 详细载荷三张表）
```

- 前后端与工具的完整约束见根目录 `AGENTS.md`（技术栈、迁移链、配色字号、每次修改必跑的检查）。
- 阶段实现细节见 `docs/phase-*.md`。

### 2. Coding 特化能力（已落地）✅

- **工作区绑定** ✅：Agent 绑定本机目录，文件工具沙箱与 Shell 执行目录跟随。
- **五个通用 Coding 工具** ✅：读文件（支持 tail_lines 尾读）、改文件（精确替换 + diff）、列目录、搜代码、Shell。
- **Shell 工程能力** ✅（阶段十四）：前台执行 / 后台托管（跨轮次存活的任务注册表 + 日志落盘）/ 停止 / 列表；前台阻塞预算保险丝（超时自动转后台不误杀）；输出头尾保留 + 全量底稿落盘；整树击杀不留垃圾进程；任务退出自动通知模型。
- **执行治理** ✅：危险命令黑名单（正则 + 分段词法双层）；执行前人工审批按档位（off / standard 高风险动作 / strict 全工具）与 Shell 命令白名单（命中免审）控制，超时按拒绝处理。
- **上下文工程** ✅：容量估算 → 自动压缩（摘要与边界存会话，聊天记录不改写）→ 备用裁剪。

## 五、核心工作流（用户视角）

```
提需求 → Agent 澄清与计划 → 分阶段执行（每阶段独立会话）
   → 每阶段：开发 → 测试 → 修复 → 自检 → 生成交接文档 → 暂停
   → 用户验收（可跳过）→ 下一阶段 → 最终验收
```

- **阶段化开发 v2（项目级多会话）** ✅：阶段确认模式下，Agent 先按意图路由判断——从 0 到 1 的开发需求走规划（`submit_stage_plan` 提交 2–8 个阶段的计划，用户确认后**每个阶段一个独立会话**逐阶段推进），存量项目增量开发 / 问答走普通流程。每阶段按「开发→自检→生成交接文档→调用 finish_stage」收尾，交接文档内容直接展示给用户；用户点「进入下一阶段 / 生成项目汇总」由后端自动新建会话并带上计划与上一阶段交接，工作区由代码钉住保证多会话一致。机制说明见 docs/phase-15.md 第八节。
- **两种自主档位** ✅（Agent 级）：阶段确认模式（默认，做完即停等人验收，提供 finish_stage 与阶段协议提示词）与高度自主模式；高风险操作在任何档位下都受审批档位约束。
- **Agent 自检 ≠ 用户验收**：自检尽量接近真实验收（跑测试、起服务、验证响应），但最终判断在用户。

## 六、评测思路（伴随建设，不另起大灶）🚧

- V1/V2 回归对比 ✅（阶段十五 demo）：同一数据集的两个任务按用例对照得分/过程分与聚合差值（评测页"回归对比"面板）；指标按任务动态选择、权重可改 📋 未实现。
- 能客观测量的不交给 LLM Judge：测试通过率、工具调用/失败次数、耗时、Token、审批/拦截数走客观数据（运行记录表已具备数据基础 ✅；曾做的工具仪表盘页面 2026-10-08 移除，指标可从运行记录详情获得）；结果质量（阶段十二）与过程合理性（阶段十五，基于真实工具事件的过程评分）由 LLM Judge 完成 ✅。

## 八、已知边界

- 沙箱为软约束（黑名单 + 审批 + 工作区限制），Shell 天然可越界可联网；强隔离需容器/受限账号，当前不做。
- 后台任务无自动超时；后端重启后的孤儿进程按登记文件尽力回收。
- 浏览器页面验收尚未建设（Agent 目前"看不见"页面，只能验证接口与日志）。
